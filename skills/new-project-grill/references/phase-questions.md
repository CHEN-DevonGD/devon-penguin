# 階段題庫

按 SKILL.md 的提問規則選題；這是可改寫的種子，不是必問題數。每張卡只問一個決策。先讀已知資訊並跳過已答項目；遇研究、試用或規格新狀況，再插入當次必要題。每題選項第一個為情境合適的推薦，最後固定「我不知道，幫我選」。兩個方向加代選通常就夠；更多方向依宿主上限拆批。

## Q01／階段 0：目標

- 問題：你最希望這個點子先幫誰，完成哪一件事？
- 先查：先讀使用者敘述、材料與專案摘要。
- 跳過：目標與使用者已清楚。
- 選項 1（推薦）：先完成一條最重要的工作流程
- 選項 2：將多種需求分開，選一種先試
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：核心驗證比較容易做完整；其餘想法先保留。
- 代選：目標不能自行捏造；給具體例子與暫定方向讓使用者修訂。

## Q02／階段 0：交付程度

- 問題：第一版想用來確認可不可行、給少量人試用，還是正式上線？
- 先查：確認使用者是否已指定 POC／試用／正式用途。
- 跳過：交付程度已確認。
- 選項 1（推薦）：快速概念驗證
- 選項 2：給真實使用者使用（再確認少量試用或正式上線）
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：還在探索時先用低投入驗證；確有正式需求就改推薦。
- 代選：探索中的點子先推薦 POC，清楚標示示範及尚未具備能力。

## Q03／階段 0：合作深度

- 問題：你希望我問到多深入？
- 先查：已有「多問／少問／先出計畫」就沿用。
- 跳過：深度已指定。
- 選項 1（推薦）：適中：問重要取捨、查主要方案
- 選項 2：快速：只問阻塞問題，先給最小計畫
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：適中能理解選擇，也保留往前推進的速度。
- 代選：採適中，可隨時改成少問或深入。

## Q04／階段 0：本次範圍

- 問題：這一輪要先交計畫，還是計畫確認後接著實作？
- 先查：讀當次要求、宿主模式及已有授權。
- 跳過：使用者已指定計畫／實作。
- 選項 1（推薦）：先交可直接開工的計畫
- 選項 2：計畫確認後接著實作
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：目標未定時先形成可 review 的方案。
- 代選：先交計畫，不把代選視為執行授權。

## Q05／階段 1：裝置

- 問題：最後要在哪些裝置上使用？
- 先查：開發端硬體與工具自行盤點；目標裝置無法讀取才問。
- 跳過：目標裝置已清楚。
- 選項 1（推薦）：先支援一個主要裝置
- 選項 2：首版就支援多種裝置
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：先把主要使用流程驗證完整，跨裝置列入必要驗收。
- 代選：按實際使用情境推薦目標，不用目前開發機代替朋友的裝置。

## Q06／階段 1：資源

- 問題：你目前有可以使用的雲端機器或服務嗎？沒有也可以。
- 先查：先查已授權可讀的資源資訊，不讀憑證。
- 跳過：資源已知或不影響選型。
- 選項 1（推薦）：先用已有本機資源評估
- 選項 2：也評估現有雲端資源
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：先避免額外成本；本機不足再按預算比較。
- 代選：先盤點已知資源，未知標待查；不假設有雲端或 GPU。

## Q07／階段 1：資料

- 問題：這個專案的資料可以交給外部服務處理嗎？
- 先查：讀資料限制與已有授權，確認是否有私人資料。
- 跳過：不用外部處理或已明確確認。
- 選項 1（推薦）：先用合成資料做本機驗證
- 選項 2：評估允許的外部處理方式
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：尚不清楚資料範圍時用合成資料先驗證。
- 代選：保留外送待確認，先查本機方案；不代替使用者授權上傳。

## Q08／階段 1：投入

- 問題：第一版願意投入多少時間與費用？
- 先查：讀使用者已給的期限、預算與已有帳號。
- 跳過：投入上限已清楚。
- 選項 1（推薦）：先用最低必要投入做出可試版本
- 選項 2：為較完整效果增加明確投入
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：上限影響現成方案與首版取捨，不要求在對話提供帳密。
- 代選：推薦可逆的小範圍，新增費用維持未授權。

## Q09／階段 2：沿用方式

- 問題：查到的成果已符合大部分需求，你希望先套用到什麼程度？
- 先查：先深入實際候選、沿用條件與差距。
- 跳過：沒有候選或使用者已有偏好。
- 選項 1（推薦）：先沿用最符合限制的成熟成果
- 選項 2：保留更大的客製範圍
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：用現有成果縮短驗證時間；具體選項要改成查得方案。
- 代選：依證據推薦，記錄基準來源與差距；沒有資料不假造候選。

## Q10／階段 2：調查深度

- 問題：目前主要方案已清楚，是否需要再查會改變選擇的部分？
- 先查：判斷剩餘不確定性是否真會改變決策。
- 跳過：證據足夠且使用者未要求深入。
- 選項 1（推薦）：先補查最大的關鍵疑慮後收斂
- 選項 2：深入比較另一條可行路線
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：把調查集中在最可能改變結果的地方。
- 代選：只查關鍵缺口，證據足夠就回到範圍與計畫。

## Q11／階段 3：必要功能

- 問題：首版如果只能完整做好一條流程，哪一條最重要？
- 先查：整理目標、現成能力與使用者已確認功能。
- 跳過：必要流程已明確。
- 選項 1（推薦）：先完成最能驗證目標的流程
- 選項 2：首版納入另一個必要流程
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：首版過大會延後回饋；推薦須跟使用者目的吻合。
- 代選：依已確認目的選最小完整流程，其他需求列為延後而不消失。

## Q12／階段 3：取捨

- 問題：依查到的方案，這個取捨你更在意哪一邊？
- 先查：先知道實際差异，例如成本／速度／效果／資料位置。
- 跳過：取捨不影響結果或已回答。
- 選項 1（推薦）：選符合已確認優先條件的方案
- 選項 2：選另一個可行方案
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：改寫成具體方案及代價，避免抽象地考技術名詞。
- 代選：比較研究證據與限制，說明推薦理由；不能猜未知事實。

## Q13／階段 4：可行性

- 問題：這個關鍵能力還沒測過，要先做小型驗證嗎？
- 先查：確認是否已有證據、允許指令／資料／資源與目前模式。
- 跳過：已驗證或不影響計畫。
- 選項 1（推薦）：在既有範圍做最小驗證
- 選項 2：先交計畫並列出待驗證條件
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：提早發現技術不通可減少後面重做。
- 代選：模式允許才做；否則寫測試設計與未驗證限制。

## Q14／階段 4：成功條件

- 問題：看到什麼實際結果，你會覺得第一版值得繼續？
- 先查：先草擬可觀察條件，避免叫新手自己寫測試規格。
- 跳過：成功條件已清楚。
- 選項 1（推薦）：用主要流程實際完成加必要測量
- 選項 2：再加一項關鍵體驗或效能要求
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：把「好不好用」換成能 review 的結果。
- 代選：依目標給可修訂條件；不承諾沒測過的速度或品質。

## Q15／階段 5：收斂

- 問題：這份計畫還有哪個會影響開工的決策需要改？
- 先查：先交完整計畫，列假設及阻塞。
- 跳過：使用者已批准，或只要求交計畫即可。
- 選項 1（推薦）：保留目前有依據的決定
- 選項 2：修改指定的目標或取捨
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：讓使用者 review 具體方案，不重新問整份訪談。
- 代選：保留可逆假設；未批准執行仍不寫程式。

## Q16／階段 6：試用回饋

- 問題：第一個可試版本最需要修哪個地方？
- 先查：先自行測試與觀察錯誤，提供實際操作入口。
- 跳過：沒有試用回饋或已指定修正。
- 選項 1（推薦）：先修影響主要流程的問題
- 選項 2：先調整關鍵體驗
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：技術錯誤由 Agent 查，使用者提供目的與感受。
- 代選：先處理主要流程，保留新功能想法供範圍判斷。

## Q17／階段 7：缺少的驗收

- 問題：哪一項需要你在實機或真實時間情境完成？
- 先查：先確認 Agent 工具能做到哪些驗證。
- 跳過：全部可實測或使用者已完成。
- 選項 1（推薦）：先完成影響使用的必要實機項目
- 選項 2：接受明列限制並延後非必要項目
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：不能把桌面模擬當成已在朋友手機測過。
- 代選：給具體清單與預期；必要驗證未完成就標示待驗證。

## Q18／階段 8：交付方式

- 問題：你要自己本機使用、讓同網路的人試用，還是交給別人／部署？
- 先查：沿用已確認目標與操作範圍。
- 跳過：交付方式已指定。
- 選項 1（推薦）：先完成已確認的最小可用交付
- 選項 2：增加其他交付場景
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：不同場景會改變啟動、資料與部署需求。
- 代選：依已有需求代選，不自行公開服務或更改 repository 可見性。

## 交付程度條件題／階段 0

- 問題：這一版是給少量人試用，還是正式開始提供服務？
- 先查：已確認要給真實使用者使用，且尚未說明成熟度。
- 跳過：交付程度已說明，或只做概念驗證。
- 選項 1（推薦）：先給少量人試用。
- 選項 2：正式上線，按實際用途確認必要條件。
- 選項 3：我不知道，幫我選。
- 白話為什麼／取捨：實際提供服務需要比試用更完整的穩定性與維護安排。
- 代選：探索期推薦少量試用；已明確需要正式用途時不能擅自降成 POC。

深入模式也可直接用自由補充或「深入一點」指定；若原生介面能呈現更多選項，可在代選前增加深入選項，不將快速與深入合成一個答案。
